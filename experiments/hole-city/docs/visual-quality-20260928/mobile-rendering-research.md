# Clean mobile rendering: practical research

Research date: 2026-09-28. Target: iPhone 14 class. This is a read-only recommendation, not a performance result or a claim about Hole.io’s internal renderer. Official engine documentation describes available techniques; proposed settings below are our starting experiments.

The useful stack is controlled shapes and colors, readable broad highlights, stable filtered textures, restrained shadows and adequate output resolution. Moving engines or raising every quality setting is not required to test these improvements.

## What official sources establish

| Topic | Documented behavior | Consequence for this project |
| --- | --- | --- |
| Geometry antialiasing | Unity distinguishes MSAA’s triangle-edge coverage from texture/specular aliasing. Its guidance includes FXAA for mobile, while also noting efficient MSAA on tile GPUs under suitable pass configurations. Godot recommends testing 2×/4× rather than costly 8×. [Unity AA](https://docs.unity.com/en-us/engine/6000.3/manual/render-pipelines/universal-render-pipeline/anti-aliasing), [Godot AA](https://docs.godotengine.org/en/stable/tutorials/3d/3d_antialiasing.html) | Compare 2×/4× on-device; MSAA cannot repair noisy highlights, tiny window patterns, faceted silhouettes or insufficient pixel resolution. |
| Resolution | URP Render Scale changes the 3D target while leaving UI native. Godot supports separate 3D scale with bilinear filtering in all renderers; lower scale saves GPU work but loses clarity. [URP asset](https://docs.unity3d.com/6000.0/Documentation/Manual/urp/universalrp-asset.html), [Godot scaling](https://docs.godotengine.org/en/stable/tutorials/3d/resolution_scaling.html) | Measure framebuffer pixels and CSS/device-pixel ratio first. Keep UI sharp; test 3D scale separately. Lower resolution is a quality tradeoff, not “lossless optimization.” |
| Shadows | A shorter shadow distance concentrates shadow-map texels. Additional point-light shadows require six directional renders; shadow cascades, soft filtering and extra lights add work. [Unity shadow resolution](https://docs.unity.com/en-us/engine/6000.3/manual/lighting-overview/lighting/shadows-in-urp/shadow-resolution-urp), [Unity shadow optimization](https://docs.unity.com/en-us/engine/6000.5/manual/lighting-overview/lighting/shadows-in-urp/shadows-optimization) | Use one sun; fit its shadow extent to the visible play area, with margin for tall buildings. Test atlas resolution and cascade count independently. |
| Texture filtering | Anisotropy improves ground textures at shallow angles with GPU cost. Godot’s linear+mipmap filters reduce distant grain; anisotropic versions also account for viewing angle. [Unity anisotropy](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Texture-anisoLevel.html), [Godot material filters](https://docs.godotengine.org/en/stable/classes/class_basematerial3d.html#enum-basematerial3d-texturefilter) | Enable and validate mips for 3D road textures; start selective anisotropy at 4×. Do not apply negative mip bias or aggressive sharpening as a blanket fix. |
| Pipeline cost | Unity recommends removing unnecessary depth/opaque copies, extra cameras, HDR and shadow passes, based on profiling. [URP performance](https://docs.unity.com/en-us/engine/6000.5/manual/render-pipelines/universal-render-pipeline/introduction/configure-for-better-performance) | Keep opaque batches and limited transparent screen coverage. Our existing single animated collection preview is consistent with this approach. |
| Godot constraints | Compatibility supports 3D MSAA but lacks built-in FXAA, TAA, FSR2 and the screen-space roughness limiter. Godot Web currently requires Compatibility/WebGL 2. Native Mobile/Metal is a separate deployment experiment. [Renderer matrix](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html), [Web export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html) | Do not promise a Unity post-processing recipe directly in our browser build. Avoid a Forward+ dependency for this art direction. |

Voodoo’s published retrospective describes specialized work on art, user experience and product refinement; it does not disclose Hole.io’s antialiasing, shader, shadow or texture settings. No public technical-art recipe for Hole.io was found in the bounded official-site search. [Voodoo retrospective](https://voodoo.io/news/10-years-at-voodoo)

## Current local evidence and proposed order

1. **Verify real output before tuning.** `project.godot` already has `msaa_3d=2`, which means **4× MSAA**, not 2×. Its 540×960 values are logical design dimensions with `canvas_items` stretching; they do not establish the actual on-device framebuffer resolution. [Godot MSAA enum](https://docs.godotengine.org/en/stable/classes/class_viewport.html#enum-viewport-msaa)
2. **Correct material consistency.** `food_surface.gd` already provides rounded food geometry; `food_glaze.gdshader` provides broad procedural reflections. Compare these with the StandardMaterial path under identical geometry/light/color. The shader explicitly converts vertex RGB from sRGB to linear, while Compatibility’s StandardMaterial vertex-sRGB flag is ineffective. This is a concrete color-mismatch hypothesis to test, not a verified rendered bug. [Godot vertex color behavior](https://docs.godotengine.org/en/stable/classes/class_basematerial3d.html#class-basematerial3d-property-vertex-color-is-srgb)
3. **Improve actual silhouettes and normals.** Add small bevels to prominent hard-edged props and use coherent smooth normals; keep low-detail distant variants. Reserve broad glossy highlights for icing, fruit and plastic; keep bread and pavement rougher. These are our art recommendations. Do not make every object equally glossy or uniformly more saturated.
4. **Fix distant texture stability.** `assets/food_city/streets.png.import` currently disables mip generation. Test mipmaps plus trilinear/4× anisotropic sampling at the real oblique camera angle. Procedural city-window lines need their own distance/frequency filtering; a texture mip setting cannot filter procedural patterns.
5. **Budget one lighting solution.** Current `game.gd` already uses one shadowed directional light and ambient fill. Test 1024 vs 2048 shadow maps with a tightly bounded visible extent; retain the lowest setting that survives slow camera pans without detached or crawling shadows. Avoid additional shadowed point lights, SSAO/SSR dependencies and bloom used to imitate highlights.
6. **Choose an explicit delivery profile.** Keep the present Compatibility browser path. For a shipping native iPhone build, compare Compatibility and Mobile/Metal on the same scene and retune color only with actual output evidence. Start at 3D scale 1.0/4× MSAA; compare 1.0/2× and 0.85/4× only if GPU measurements justify them. Preserve native-resolution UI. These are candidate profiles, not certified iPhone settings.

## Acceptance criteria for the next implementation

- Capture real device frames at the same camera poses: street signs/vehicle edges, building windows, glossy food pile and all UI text. Record build hash, renderer, actual framebuffer dimensions, scale, AA, iOS/browser version and device. Offline showcase frames are not substitutes.
- Test slow pans and fast swallowing: no unstable thin-line shimmer, highlight sparkle, obvious polygon corners on hero objects, shadow detachment or blurry UI at normal phone viewing size. Record A/B clips so an independent reviewer can reject cosmetic regressions.
- Run both maps and the dense collapse/rain case for ten active minutes after warmup on an iPhone 14, unplugged with normal power mode. Proposed gate: median refresh near 16.67 ms, p95 displayed-frame interval ≤18 ms, fewer than 1% intervals over 25 ms, and no sustained one-second window below 55 fps. Report thermal behavior and worst-case stalls, not only an average.
- Separate CPU simulation, GPU cost and displayed cadence. Browser `requestAnimationFrame` telemetry can reveal missed display deadlines; it cannot attribute GPU time. Native profiling should use device CPU/GPU tools. Pause, hidden tabs and loading are excluded but separately reported. A measured failure triggers a documented quality or workload change; it does not justify an unmeasured 60 fps claim.

Only this research document was created. No runtime settings, assets, tests, installs or player data were changed.
