# Resident Contact Memory v1 (Proposal)

## Evidence and purpose

The town retains its complete life-event history, but a resident's current model request is bounded to the latest 16 `experiences` in `town_turns.gd`. Previous-decision memory is the resident's own recent decision/consequence context; skill notices and referrals are explicitly attributed skill claims. These surfaces do not supply a stable, directly sourced record of who spoke to whom.

Checkpoint `seq000344-0e13bfddcb4918ba` contains three direct Ari/Fern utterances at seq 152, 154, and 172. None remains in Fern's latest-16 experience page, and her latest six decisions do not mention Ari. Ari still has seq172 in his own latest-16 page; the gap is not symmetric. All three events remain in canonical history. This is a demonstrated prompt paging gap, not lost authoritative history. The usefulness test is narrow: help a resident recognize the other speaker and resume a direct conversation without treating the old words as world truth.

## Proposed derived API

Implement `res://core/town_contact_memory.gd` as a pure projection of retained authoritative events, with an instance method equivalent to:

```gdscript
TownContactMemory.project(life_events: Array, resident_id: String,
    active_resident_ids: Array, max_contacts: int = 8) -> Dictionary
```

Return `{ "ok": true, "contacts": [...], "total_contacts": N, "has_more": bool }`. `total_contacts` is the complete number of valid distinct direct counterparts in history; `has_more` is true when the row cap hides one or more. Rows sort by `last_contact_seq` descending, then counterpart ID ascending; `max_contacts` is clamped to 0–8. If any excerpts or lower-priority rows are omitted to enforce the complete projection's hard 4 KiB UTF-8 JSON cap, also return explicit truncation/omission metadata. Never silently turn a capped list into an exhaustive-looking one.

Each row has only `resident_id`, first/last contact sequence, direct utterance counts by direction, a constant `statement_status: "speaker_statement_not_verified_world_fact"`, and `latest_direct_statements`. Each statement carries its source `event_id`, sequence, `speaker_id`, exact leading excerpt capped at 96 characters, and `truncated` flag. Keep at most the latest statement from each direction, sorted by source sequence. On seq344, Fern's latest direct statement to Ari is event `life_event_154` and Ari's latest statement to Fern is `life_event_172`; those exact source-linked excerpts fit the complete per-resident 4 KiB cap. Counts still cover all valid historical events even when statement excerpts are bounded.

Only a valid `resident_said` event contributes: unique nonempty event ID, unique positive integral sequence, nonempty utterance, distinct active actor and subject IDs, and exactly those two IDs as recipients. Both participants get reciprocal contact rows, but no observer/co-recipient does. Exclude visitor inquiries, observations, malformed/mismatched recipients, self-talk, inactive identities, and invalid or duplicate events. Statements remain attributed speech, not water-source facts, knowledge, trust, friendship, skill, agreement, consent, privacy disclosure, or authority.

Derive the output on demand; do not persist a redundant canonical relationship namespace. The function must not mutate input and must produce identical output after cold restore from the same retained event log. Deterministic row and statement ordering, explicit omitted-contact metadata, excerpt bounds, and a hard whole-projection UTF-8 cap are part of the contract.

## Resident-view and request integration gate

Production integration must place the exact derived object in the speaker's personal `resident_view.known_contacts`, preserve it through the real `TownTurns` request and `ResidentBrain` prepared payload, and explicitly pass only the bounded, allowlisted fields through `BudgetGatewayProvider`. Verify the full path with a stub brain and a no-network prepared-request assertion; never charge a model call to test projection delivery. The contract fixture must also prove visitor/privacy and third-party co-recipient rows do not enter another resident's view. This integration is absent until those checks pass.

`game/tests/town_contact_memory_acceptance.gd` reproduces seq344 page-out and calls the production API when present. Until `res://core/town_contact_memory.gd` exists, it reports `production_api_missing` and fails rather than passing a duplicate reference algorithm. Use an isolated copy of the immutable checkpoint as `--town-save`; the fixture's stubbrain request path may write only its own temporary copy.

This is a small continuity aid, not an N5 completion claim or an additional adoption gate. The meaningful project outcome remains an observable same-lineage need → GM improvement → resident effects loop.
